Here’s the current state of the character memory / player-history system as it exists today.

**Bottom Line**
- There is a real memory subsystem in place.
- It is **player-scoped**, stored in SQLite, and keyed by `player_id` plus `player-owned character instance id`.
- There are really **two layers**:
  1. a richer LLM-backed memory pipeline
  2. a simpler event log pipeline
- The richer pipeline is currently used mainly through the **admin memory tool**, not normal Discord character interaction yet.
- Battle/mission play currently writes into the **event log**, but those combat events are **not automatically distilled into memories/facts/relationships** afterward.

**Core Models**
The memory domain is defined in [main_character_memory.py:13](D:\Documents\programming\Scion%20of%20Humanity\TheArchitect\TheArchitect\src\domain\main_character_memory.py:13).

It contains:
- `EventRecord`: raw history event
- `CharacterMemory`: episodic memory for one character
- `SemanticFact`: durable fact/belief for one character
- `Relationship`: directional relationship values from one character to another
- `LLMTurnLog`: stored prompt/output log for generated turns

Important detail:
- `Relationship` is **directional**, not shared. `A -> B` and `B -> A` are separate records.
- `CharacterMemory`, `SemanticFact`, and `Relationship` all belong to a specific player-owned character instance, not a global template character.

**How the Rich LLM Memory Flow Works**
`generate_turn(...)` is the full pipeline.

Flow:
1. verify OpenAI is configured
2. load the player-owned `MainCharacter`
3. build a prompt packet from:
   - character sheet
   - scene frame
   - relationships
   - recalled memories
   - semantic facts
   - knowledge constraints
4. call OpenAI for the character turn
5. store an `EventRecord`
6. distill memories for participants
7. create/update:
   - `CharacterMemory`
   - `SemanticFact`
   - `Relationship`
8. optionally reflect into higher-level facts
9. store an `LLMTurnLog`

This is the only place where the full memory stack is created automatically.

**How Retrieval Works**
`build_prompt_packet(...)` is already fairly real.

It:
- embeds the current scene query
- loads recent memories
- loads tag-matched memories
- scores memories by:
  - cosine similarity
  - recency decay
  - importance
  - small participant/relationship boosts
- does the same for facts
- marks recalled memories with `last_recalled_at` and increments `recall_count`

Important limitation:
- prompt retrieval uses **memories/facts/relationships**
- it does **not** directly retrieve raw `EventRecord`s into the prompt

So if something only exists as an event and was never distilled, it is basically history storage, not active memory.

**Who Gets Battle Memory Events**
Only allied player-owned `MainCharacter`s get included in battle memory logging.

The bridge filters participants by:
- ally side only
- must resolve back to a player-owned source character
- must be a `MainCharacter`

So currently:
- player `MainCharacter`s get combat event history
- enemy NPCs do not
- ordinary non-main characters do not
- non-player NPC allies do not

**Most Important Gaps / Decision Points**
These are the main places we’ll need decisions next.

1. **Should `EventRecord` become the true player history log?**
- Right now it already serves that role implicitly.
- But it lacks a dedicated player-wide query/read surface.

2. **Should external events auto-distill?**
- Currently only `generate_turn()` creates memories/facts/relationships.
- Combat/mission events do not.
- If we want gameplay to shape memory naturally, this is the biggest missing step.

3. **Should memory stay `MainCharacter`-only?**
- Current service explicitly restricts v1 to `MainCharacter`s.
- That keeps it manageable, but it’s a hard boundary.

4. **How much of the prompt should use raw events vs distilled memories?**
- Current retrieval ignores raw events.
- That keeps prompts cleaner, but means fresh combat events are inert until distilled.

5. **Do we want a true player-wide narrative history view?**
- Current admin tool is character-centric.
- There is no dedicated “show me this player’s narrative timeline” tool.

**My Read**
The groundwork is better than “half-built.” The storage model and service boundaries are solid. The real missing piece is that the system currently splits into:
- `generate_turn()` = rich memory path
- `append_manual_event()` = raw log path

That split is why the feature feels present but not yet fully alive in gameplay.
